# Triton on Turing, Ampere and Ada (sm_75, sm_80, sm_86, sm_89), verified with Triton 3.8

Part of the `triton-kernels` skill. The family facts beyond Triton are in the
`gpu-architectures` skill (`turing.md`, `ampere.md`, `ada.md`).

How these facts were checked: `triton.compile` for `GPUTarget("cuda", cc, 32)` on the CPU,
and runs of the older arch's PTX on an RTX 5070 Ti through the driver JIT (correctness
only). No Triton kernel has run on a Turing, Ampere or Ada GPU yet. Scripts and raw output:
`docs/research-scripts/older-gpus-259/` (`lowering_triton.txt`, `ptx_jit_triton.txt`).

## What `tl.dot` becomes

Measured with a K-loop GEMM: 64 x 64 x 64 tiles, 4 warps, `num_stages=3`, pointers 16-byte
aligned.

| operands | sm_75 | sm_80 / sm_86 | sm_89 |
|---|---|---|---|
| fp16, bf16 | FMA: no `mma`, no `ldmatrix`, no `cp.async` | `mma.sync m16n8k16` (fp32 accumulation), `ldmatrix`, `cp.async` | as sm_80 |
| fp32, default `input_precision="tf32"` | FMA | **TF32** `mma.sync m16n8k8`, which rounds the inputs to TF32 | as sm_80 |
| fp32, `input_precision="ieee"` | FMA | FMA (still pipelined with `cp.async`) | FMA |
| int8 (`out_dtype=tl.int32`) | **does not compile**: `PassManager::run failed` in `TritonGPUAccelerateMatmul` | `mma.sync m16n8k32 .satfinite.s32.s8.s8.s32`, `cp.async` | as sm_80 |
| `fp8e4nv` (e4m3) | refused: "type fp8e4nv not supported in this architecture" | refused | `mma.sync m16n8k32 .f32.e4m3.e4m3.f32` (QMMA), `cp.async` |
| `fp8e5` (e5m2) | FMA | converted to fp16, then `mma m16n8k16` f16 | `mma m16n8k32 .f32.e5m2.e5m2.f32` |
| `fp8e4b15` | FMA | converted to fp16, then `mma m16n8k16` f16 | converted to fp16 (not QMMA) |
| `tl.dot_scaled` e4m3 (unit ue8m0 scales) | refused (e4m3) | refused (e4m3) | **emulated**: bf16 `mma m16n8k16`, no FP8 instruction |

The same tile needs 16 KB of shared memory on sm_75 (no pipelining) and 32 KB with 3 stages
on sm_80+ (fp16). The opt-in limit per block is 64 KB on sm_75, 163 KB on sm_80 and 99 KB on
sm_86 / sm_89: a config tuned on an A100 can raise `OutOfResources` on an A10 or L4.

Consequences:

* **sm_75:** use Triton for memory-bound kernels (norms, elementwise ops, reductions,
  quantisation). Put GEMMs and attention on cuBLAS fp16, CUDA C++ `mma.sync m16n8k8` or
  TileLang. Triton has no tensor-core path on Turing, and INT8 W8A8 cannot use Triton there.
* **fp32 models on sm_80+:** a fp32 `tl.dot` silently uses TF32. Use
  `input_precision="ieee"` when the exact tier compares against cuBLAS fp32, which PyTorch
  2.14 runs without TF32 (`torch.backends.cuda.matmul.allow_tf32` is False by default).
* **e5m2 or e4b15 weights on Ampere** compute in fp16 after a conversion. They save bytes,
  not tensor-core time.
* **FP8 on Ada:** plain `tl.dot` on e4m3, never `tl.dot_scaled` (bf16 emulation on sm_89).

## `cp.async` needs alignment

`cp.async` copies 4, 8 or 16 bytes (PTX ISA). A JIT launch specialises 16-byte aligned
pointers and integer arguments divisible by 16 (`tt.divisibility`), so its loads vectorise.
The checks below show the difference:

* A compile-only check without `attrs` sees unaligned pointers. The fp16 GEMM above then
  shows `cp.async 0` on sm_80 and sm_89; the fp32 one (4-byte elements) still gets
  `cp.async`.
* With `attrs={(i,): [["tt.divisibility", 16]]}` on the pointer and size arguments it
  shows `cp.async 24`.
* `examples/triton_fp8_w8a8_gemm.py`'s `gemm_ptx` helper passes these hints, so its PTX
  matches a launch: 24 `cp.async` on sm_89 and on sm_120. Under emulated sm_89 the
  **launched** GEMM also had 24 `cp.async`, 32 KB of shared memory, and a rel L2 error of
  0.0368 against `nn.Linear` (bf16).
* So check pipelining on the PTX of a launch (`kernel[grid](...).asm["ptx"]`), or pass
  `attrs`.

## Run an older arch's lowering on a newer GPU

Patch three things in the process: `driver.active.get_current_target`,
`CompiledKernel._init_handles` (load the PTX, not the cubin) and
`torch.cuda.get_device_capability`. The recipe is in the `gpu-architectures` skill's
`measure-first.md`, the script is `ptx_jit_triton.py`. It checks correctness, never speed.

Results on the RTX 5070 Ti (rel L2 error; correctness only, performance not measured):

| kernel | sm_75 | sm_86 | sm_89 |
|---|---|---|---|
| fp16 / bf16 `tl.dot` GEMM (fp32 out) | 4.1e-7 / 1.8e-7 (FMA) | 6.6e-7 / 4.8e-7 (`m16n8k16`, `cp.async`) | 6.6e-7 / 4.8e-7 (`m16n8k16`, `cp.async`) |
| `triton_rmsnorm.py` (fp16 / bf16) | < 5e-5 / < 5e-5 | < 5e-5 / < 5e-5 | < 5e-5 / < 5e-5 |
| `triton_short_attention.py` vs fp32 SDPA (fp16 / bf16) | 0.0003 / 0.0020 (FMA) | 0.0003 / 0.0020 | 0.0003 / 0.0020 |
| `triton_int8_w8a8_gemm.py` | not run: `build()` keeps the reference below sm_80 (the int8 dot does not compile) | 0.0091 (`m16n8k32` s8, `cp.async`) | 0.0091 |
| `triton_fp8_w8a8_gemm.py` | not run: `build()` keeps the reference below sm_89 | not run: `build()` keeps the reference below sm_89 | 0.0368 (QMMA, `cp.async`) |
